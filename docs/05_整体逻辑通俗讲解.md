# 云台代码整体逻辑（通俗版）

这份文档不讲公式，只讲"这套代码到底在干什么、为什么这么干"。
看完应该能回答："为什么电机不动？""为什么俯仰和偏航不一样？"
"我该动哪个参数？"

---

## 一、一句话分工

```
   云台（H723）负责「稳」    —— 快，200~500Hz，用陀螺/IMU 顶住车体晃动
   机载计算机  负责「准」    —— 慢，30~60Hz，看着图像把激光逼到靶心上
   两者之间只传一个量：「角度偏置」
```

为什么这么分？因为**延迟要求完全不同**：
电机要 200Hz 以上、还不能被系统调度抖动污染，所以必须在 MCU 里；
而视觉算力需求大、只要几十赫兹，所以在机载计算机里。
中间用"角度偏置"这个**低频小量**连起来，串口那几毫秒延迟根本不算事。

**最关键的改动就一句**：

> 偏航目标 = 上电锁定的朝向 + 上位机给的偏航偏置
> 俯仰目标 = 上电锁定的角度 + 上位机给的俯仰偏置

也就是说，**稳定能力一点没动**，只是把"要稳定到的那个方向"挪了一点。

## 二、上电之后，云台自己会做什么（6 步，约 3.5 秒）

这一段是代码里最"死板"的部分，但每一步都有血泪教训。

| 步 | 干什么 | 为什么必须这样 |
|---|---|---|
| 1 | 初始化 IMU（BMI088），失败就每 0.5s 重试 | 没 IMU 就没法控制，这是启动路径上**唯一**的等待条件 |
| 2 | **纯等 2 秒** | 驱动器上电自检需要时间。控制模式指令发太早会被忽略 —— 这就是历史上"上电偶尔完全失去控制"的根因 |
| 3 | 发一次"进入闭环"（0x00A2） | 让驱动器开始接受指令 |
| 4 | 发一次"速度模式"（0x0060=1） | 两个电机都工作在速度模式，位置环由 MCU 自己算 |
| 5 | 锁基准：把当前朝向、当前俯仰角记下来 | 之后所有偏置都是相对这个基准的增量 |
| 6 | 进 RUNNING，开始每 5ms 发速度指令 | 电机从"软"变"硬" |

**为什么第 2、3、4 步全是"纯延时/只发一次"，而不写成"等到某个条件满足"？**

这是踩过的坑：带条件的启动逻辑，一旦条件因为噪声或环境影响永远不满足，
整个状态机就停在原地 —— 而表现是"云台一直是软的、能被手掰动"，
**极难定位**。所以规矩是：

> 启动路径上只允许纯延时推进；
> 带条件的逻辑只能放在 RUNNING 里做"后台降级"。

另外 0x00A2 和 0x0060 **只在启动时发一次，运行期绝不再碰** ——
反复写这两个寄存器会不断复位驱动器内部的运动状态，
表现是"水平电机完全不动"（偏航指令本来就只有几 rpm，一复位更起不来；
俯仰因为前馈指令大，复位后还能立刻重新脱困，所以看不出问题）。

## 三、运行中，每 5ms 转一圈的循环

```
每 2ms：读一次 IMU（陀螺+加速度计）-> Mahony 姿态解算 -> 得到偏航/俯仰/横滚角

每 5ms：
   ① 收 CAN 反馈  —— 抽出驱动器回帧里的"电机当前角度"
   ② 看上位机要什么 —— 从串口收到的最新命令（模式 + 偏航偏置 + 俯仰偏置）
   ③ 算偏航指令
   ④ 算俯仰指令
   ⑤ 把两条速度指令发给两个驱动器
   ⑥ 顺手把状态填好，交给链路上报

每 20ms：往机载计算机发一帧遥测（姿态、电机角、陀螺、状态、故障码）
```

## 四、两个轴为什么用完全不同的控制方式（最容易搞错的地方）

先记住一个硬件事实：

> **IMU 装在「中间平台」上 —— 偏航电机之上、俯仰电机之下。**

```
        底盘（小车）
          └─ 偏航电机（水平转）
               └─ 中间平台   ← IMU 装在这里
                    └─ 俯仰电机（上下转）
                         └─ 激光
```

于是有个决定性的区别。判据只有一句话：**我让这个电机动一下，这个传感器的读数会不会跟着变？**

| | 偏航电机转 | 俯仰电机转 |
|---|---|---|
| IMU 姿态角 | 跟着变 ✅ | **完全不变** ❌ |
| 电机自己的编码器 | 跟着变 ✅ | 跟着变 ✅ |

结论：

* **偏航**：IMU 看得见偏航电机的动作 -> 直接把 IMU 测出的角度当反馈做闭环。
* **俯仰**：IMU **看不见**俯仰电机的动作 -> **绝对不能拿 IMU 角度当反馈**。
  硬这么做的话，控制器会认为"我推了它却毫无反应"，于是拼命加大输出，
  电机朝一个方向狂奔（这个现象实测复现过）。
  -> 俯仰只能用**电机自己的编码器**当反馈。

所以在俯仰环里，IMU 的角色完全变了：它不是反馈，而是
**"扰动测量器"** —— 它测到的俯仰角变化只可能来自车体倾斜，
所以它负责回答"目标角应该是多少"，**不回答**"现在到哪儿了"。

> 一句话记住：**偏航靠 IMU 当反馈，俯仰靠 IMU 生成目标、靠编码器测量结果。**

## 五、两个环各自怎么算

### 偏航环

```
误差 = 目标朝向 - IMU 测出的当前朝向
输出 = 角度PID(误差)  +  陀螺前馈(绕竖直轴的角速度)
```

为什么要有**前馈**那一项？因为电机有静摩擦脱困门槛（约 10rpm）：
角度 PID 的比例项在误差很小时输出很小（差 1° 只有 3.5rpm），根本推不动电机，
看起来就像"坏了"。前馈一来就是几十 rpm，直接越过门槛，
**手一动电机立刻跟着动**；角度 PID 则退居二线，只负责慢慢把角度精修回去。

### 俯仰环

```
目标角 = 上电锁定的电机角 + 上位机给的俯仰偏置
误差   = 目标角 - 电机编码器测出的当前角
输出   = 位置PID(误差)  +  陀螺前馈(绕水平轴的角速度)
```

**俯仰比例增益的稳定上限（这里之前算错过一次，代价是"手一碰俯仰就前后越抖越大"）**：

```
每拍的环路增益 = 6 × KP × dt
   （6 是 rpm -> °/s 的换算：1 rpm = 6 °/s）
稳定要求它 < 2，考虑驱动器速度环延迟还要留余量
即  KP < 1/(3·dt)

  dt = 5ms 时：
    KP = 100 -> 每拍增益 3.0  -> 【发散】
                 1° 误差一拍推过 3°，下一拍反向推 6°，再下一拍 12°……
                 手一碰就越抖越大
    KP =  15 -> 每拍增益 0.45 -> 稳定（能覆盖速度环延迟到 30ms 的最坏情况）
```

之前误写成"环路带宽 = KP/6"（把换算关系搞反了），于是得出"KP=100 没问题"的
错误结论。真实带宽是 **6×KP = 600 rad/s**，而采样只有 200Hz —— 差了 3 倍，
必然振荡。

> **KP 调小 ≠ 变慢**：定位精度由积分项和外层视觉环保证，
> 内环只需要"稳 + 抗扰"。仿真（速度环 5~30ms、往返延迟 1~2 拍）末段残差
> ≤0.063°，折算到 1.1m 处 ≤1.2mm。

### 为什么"手掰一下，俯仰就抖起来"

**先纠正一个很容易搞反的地方**：IMU 装在俯仰电机**下面**的中间平台上，
所以俯仰电机自己转，IMU 是**看不见**的（见本文件第四节的表）。
这意味着：

> 用手掰【俯仰轴】这个动作，陀螺前馈**根本不参与** ——
> 会抖，只能是【电机编码器位置环】自己的问题。
> 前馈在这里是替罪羊。

位置环为什么会自激？因为它不是直接给力矩，而是"发速度指令给驱动器"，
而驱动器内部**还有一个速度环**，那个速度环本身有 20~50ms 的延迟：

```
  位置环(每 5ms 算一次) -> 速度指令 -> 驱动器速度环(慢) -> 电机 -> 编码器 -> 回来
                                        ^^^^^^^^^^^^^^^^
                                        相位就是在这里落后的
```

判据还是那条（T_delay 取驱动器速度环 + 反馈的等效延迟）：

```
  每拍环路增益 = 6 × KP × T_delay，要求 < 2

  T_delay ≈ 30ms 时：  KP < 11
  KP = 100 -> 环路增益 10  -> 猛烈发散（实测：越抖越大）
  KP =  15 -> 环路增益 2.7 -> 仍在边界外，被摩擦/饱和限制成"
                              有界等幅抖动"（实测：幅度变小、手扶就稳）
  KP =   8 -> 环路增益 1.4 -> 稳定，还有余量
```

这正好解释了实测现象：**KP 从 100 降到 15，只是把"越抖越大"压成了
"有界抖动"，并没有把它压进稳定区**。手扶能稳，是因为手加了阻尼，
掩盖了问题；根本解法是把 KP 再降一档。

抖动的**频率**能进一步区分病因（`tools/tune_pitch.py` 会自动算）：

| 频率 | 病因 | 对策 |
|---|---|---|
| > 3 Hz | 增益型自激（KP 相对延迟太大） | 降 KP：15 → 8 |
| < 2 Hz | 积分/静摩擦型极限环（KI 太大、机构有间隙） | 降 KI、加大死区 |

那前馈的符号怎么测？必须**倾【底座/车体】**（那才是 IMU 看得见的运动），
做法是前后点动几次，同时看陀螺俯仰角速度和俯仰电机角速度：

```
  底座低头(陀螺 > 0) -> 电机应该反向转(θ' < 0) -> 相关系数为【负】才对
  相关系数为正 = 前馈在帮倒忙，符号要取反
```

`tools/tune_pitch.py` 的 `f` 命令会自动算这个相关系数。

**还有一条和它配对的功能：平台俯仰补偿（`PITCH_PLAT_COMP`，默认已打开）。**

俯仰位置环量的是"电机相对底座"的角度，**底座整体倾斜时这个角根本不变**，
位置环误差为 0，于是电机一动不动、镜头跟着底座一起低头。
位置环自己永远不会发现这件事，必须由 IMU 把"世界倾斜了多少"告诉它：

```
俯仰目标 = 上电锁定的电机角 + 上位机偏置 - 平台俯仰变化量 × 补偿符号

  陀螺前馈      ：管【正在倾斜】的那一瞬间（快，无绝对基准）
  平台俯仰补偿  ：管【倾斜之后的持续角度】（慢，有绝对基准）
  两个都要有，缺一个就是"倾斜完就偏"
```

符号关系：**补偿符号 = −前馈符号**（老固件实测是 FF=−1、COMP=+1，
新固件沿用这个组合）。现场可以用 `c 0/1/-1` 在线开关和换符号，
判据很简单：慢慢把底座倾斜 10°，靶面光斑**基本不动**就对了。

估计"倾斜了多少"用的是互补滤波：陀螺积分管快（不受车加减速影响），
Mahony 姿态角管慢（重力做基准、不会长期漂）。补偿目标还做了
60°/s 的变化率限幅，所以即使符号判错也只会"慢慢歪"，不会一甩甩飞。

现场不用改代码重新烧写，直接用
`rdk_aim/tools/tune_pitch.py`（0x15 PARAM 在线调参）几秒就能试完一个组合，
它还会自动算出"掰一下松手后是收敛还是发散"。用法见
`rdk_aim/docs/06_运行命令速查.md` 第 5.5 节。

## 六、代码里每一层在"防什么"

这部分是这套代码真正花心思的地方 —— 每一项都对应一次踩坑：

| 防什么 | 怎么防 | 出问题的表现 |
|---|---|---|
| **启动卡死** | 启动路径只用纯延时，不带条件 | 云台一直是软的、能被手掰动 |
| **俯仰飞车** | 方向反了/机构卡死时，误差持续 >25° 达 400ms 就自动降级成纯陀螺前馈并报故障 | 电机朝一个方向猛转不停 |
| **编码器掉线** | 50ms 收不到反馈就退化成纯前馈，并报故障 | "俯仰只对快动有响应、慢慢倾斜没反应" |
| **底座整体倾斜、镜头跟着跑** | IMU 测出平台俯仰变化，把俯仰目标反向挪同样角度（平台补偿），快的那部分交给陀螺前馈 | 云台整体低头时俯仰电机纹丝不动，激光从靶心跑掉 |
| **上位机掉线** | 0.5s 收不到 AIM 就自动切回 STAB（保持朝向）+ 关激光 | 上位机崩了，云台仍稳定，只是不再瞄准 |
| **偏置给飞了** | 偏航偏置限 ±180°、俯仰限 ±80°，再加 ±80° 行程软限位 | 撞机构、扯线 |
| **绕线** | 把"电机相对车身的转角"持续上报给上位机；专门做了 UNWIND 解绕模式 | 跑一圈相对角净变化 -360°，两圈就把线拧死 |
| **发送卡死** | 发送通道超过 100ms 没完成就强制恢复 | 上位机收不到数据，但 H723 还在跑（最难查的一类） |
| **调试文本冲乱协议** | 日志打包成 TEXT 消息发，不直接 printf | 上位机 crc_err 暴涨、时好时坏 |

## 七、出问题怎么自己定位（照这个顺序查）

### 最快的自检：**不上位机也能试**

烧写后上电，**等 4 秒**，用手掰云台 —— 应该明显变"硬"（能感到电机在抗）。

| 现象 | 说明 | 查什么 |
|---|---|---|
| 4 秒后变硬 | 固件正常走完启动、两个电机都在闭环里 | 继续调瞄准 |
| 一直软的 | 没走到 RUNNING | 看下一条 |

### 接上地瓜派看日志

```bash
python main.py ping --port /dev/ttyS1
```

启动日志按顺序是（**缺哪条就卡在哪一步**）：

```
[H723] === YunTai Start ===
[H723] [BMI088] try #1 ...
[H723] [BMI088] result=0
[H723] [BMI088] OK -> motor boot delay
[H723] [MOTOR] boot delay done
[H723] [MOTOR] enter closed loop
[H723] [MOTOR] set speed mode
[H723] [IMU] locking reference ...
[H723] [REF] pitch_motor(deg)=xx.xx     <-- 这个数不是 0 才说明编码器通了
[H723] === STABILIZATION ACTIVE ===
```

### 连日志都收不到

把 `Core/Inc/debug_uart.h` 里的 `DEBUG_RAW_UART` 改成 **1** 重新烧写，
用普通串口助手（115200）接 USART1 就能直接看到文本日志。
这一步能区分"是 H723 本身没跑起来"还是"串口链路不对"。

### 还能用调试器

CubeIDE 里 Debug 运行，看全局变量 `g_state`：

```
0 = BMI088 初始化中   1 = 等驱动器自检   2 = 进闭环   3 = 切速度模式
4 = 锁基准中          5 = RUNNING（正常）
```

停在 5 而电机不动 -> 问题在 CAN / 驱动器 / 供电，不在控制逻辑。

## 八、想调参的话，只看这几个（都在 yuntai_task.c 顶部）

| 现象 | 改哪个 | 往哪改 |
|---|---|---|
| 偏航慢漂跟不回来 | `YAW_KI` | 加大 |
| 偏航抖动 | `YAW_KP` | 减小 |
| 快速扭底盘时偏航跟不上 | `YAW_FF_RPM_PER_RADS` | 加大 |
| **光斑总差几毫米停不进去** | `PITCH_KP` | 加大 |
| 俯仰电机持续"滋滋"响 | `PITCH_KP` | 减小 |
| 快速前后倾时俯仰跟不上 | `PITCH_FF_RPM_PER_RADS` | 加大 |
| 底盘转动时电机"没反应" | `YAW_FF_SIGN` / `PITCH_FF_SIGN` | 取反试试 |

上面这些参数现在**都可以在线改**（不用重新烧写）：H723 支持 0x15 PARAM 消息，
地瓜派上用 `python3 tools/tune_pitch.py` 就能改，掉电恢复默认值。
现场调出满意的数，再写回 `yuntai_task.c` 的 `#define` 固化。

⚠ 唯一**不要随便改小**的是 `MOTOR_BOOT_DELAY_MS`（默认 2000）：
改小了驱动器可能还没自检完，表现就是"上电偶尔完全失去控制"。
