控制原理本身见 `docs/控制逻辑说明.md`，串口协议逐字节定义见

## 一、这次改了什么

目标只有一句话：**让云台在保持稳定的前提下，能接受机载计算机下发的瞄准偏置。**

### 新增文件

| 文件 | 作用 |
|---|---|
| `Core/Inc/gimbal_proto.h`<br>`Core/Src/gimbal_proto.c` | 纯协议层：CRC16、组帧/拆帧、消息编解码。**不含 HAL**，所以能在 PC 上单测 |
| `Core/Inc/gimbal_link.h`<br>`Core/Src/gimbal_link.c` | 链路层：USART1 中断收发、命令解释、遥测上报、看门狗 |

### 改动的文件

| 文件 | 改了什么 |
|---|---|
| `Core/Src/yuntai_task.c` | **重写**。加上俯仰编码器位置环、偏置叠加、激光输出、解绕模式、故障上报 |
| `Core/Src/jc4310.c/.h` | 新增 `jc_read_position()` / `jc_parse_speed_reply()` / `jc_parse_position_reply()` |
| `Core/Src/can_bsp.c/.h` | 新增接收邮箱（4 深），中断里把 FIFO 抽干；新增 `fdcanx_receive_frame()` |
| `Core/Src/debug_uart.c` | `debug_print` 改走协议 TEXT 消息（不再直接 printf 到 USART1） |
| `Core/Src/main.c` | `gimbal_link_init()` 在 `yuntai_init()` 之前调用 |
| `Core/Src/stm32h7xx_it.c` | 新增 `USART1_IRQHandler`（在 USER CODE BEGIN 1 里，重新生成代码不会丢） |

### 三个关键设计决定

1. **收只用 RXNE 中断 + 软件环形缓冲**，不改 `.ioc`、不用 DMA。
   中断里只做"存一个字节"，解析全在主循环。115200 下 11.5k 中断/s，
   对 550MHz 的 H723 不算负担。
2. **发用 `HAL_UART_Transmit_IT` + 发送环形缓冲**，绝不阻塞主循环。
   若用阻塞发送，一帧 28 字节要 2.4ms，会把 2ms 的 IMU 节拍拖歪。
3. **调试文本走协议（TEXT 消息）**，不再直接 printf。
   否则文本会把二进制帧冲乱，现象是上位机 crc_err 暴涨、时好时坏，极难查。

另外还加了一条**就绪标志位** `GP_ST_READY`（遥测 flags 的 bit4）：
上位机判断"云台起来了没有"只认这一位，不去比 `state` 数值。
（踩过这个坑：状态机去掉一个 INIT 状态后 RUNNING 从 6 变成 5，
上位机一直卡在 `BOOT_WAIT`。数值会变，标志位不会。）

## 二、接线（3 根线，不要接电源）

```
   地瓜派转接板串口               H723 (USART1)
        TX  ────────────────────►  PA10 (USART1_RX)
        RX  ◄────────────────────  PA9  (USART1_TX)
        GND ────────────────────   GND
```

| 项目 | 值 |
|---|---|
| 波特率 | **115200**（两边必须一致；H723 侧就是 `MX_USART1_UART_Init()` 里的 115200） |
| 电平 | 3.3V TTL，不要接 5V |
| 地瓜派设备名 | 40PIN 排针串口是 `/dev/ttyS1`；USB 转串口是 `/dev/ttyUSB0`。用 `python main.py ports` 确认 |
| 权限 | `sudo usermod -aG dialout $USER` 后**重新登录**，否则打不开串口 |

> 只接 TX/RX 两根、不共地是**一定不通**的，这是最常见的坑。

## 三·补：第一次烧录"两个电机完全没反应"的原因（已修复）

**现象**：烧写后云台上电，两个电机从头到尾一点反应都没有（全程是软的、
能被手掰动）。串口那边也收不到任何日志。

**根因**：`USART1_IRQHandler` 里少了一行 —— 只处理了接收，
没有把中断交给 `HAL_UART_IRQHandler`。链条是这样的：

```
HAL_UART_Transmit_IT() 内部执行 CR1 |= TXEIE   （打开"发送寄存器空"中断）
        ↓
USART 的 TDR 空闲时，TXE 标志【一直是置位】的
        ↓
所以打开 TXEIE 会【立刻】触发中断；只有写一次 TDR 才能把 TXE 清掉
        ↓
而我们的中断函数没调用 HAL_UART_IRQHandler -> 没人去写 TDR
        ↓
TXE 永远是 1 -> 中断被无限重复触发（中断风暴）
        ↓
主循环被彻底饿死，一行代码都跑不到
        ↓
状态机永远走不到 RUNNING -> 两个电机收不到任何速度指令
```

**修复**（`Core/Src/stm32h7xx_it.c`，一行）：

```c
void USART1_IRQHandler(void)
{
  gimbal_link_rx_isr();          /* 1) 接收：自己读 RDR 存进环形缓冲 */
  HAL_UART_IRQHandler(&huart1);  /* 2) 发送/错误：必须交给 HAL 去写 TDR */
}
```

**教训（重要）**：

> 只要用了 HAL 的 `xxx_IT` 系列（中断方式收发），
> 就必须让 `HAL_UART_IRQHandler()` 进到同一个中断里。
> 自己写 ISR 可以，但只能是"额外加一段"，
> **不能把 HAL 原来的那份替换掉**。
>
> 这类 bug 的危险之处在于：程序不报错、不崩、就是**什么都不干**，
> 从"电机没反应"这个现象完全猜不到是串口中断的问题。

### 顺手加的排障开关

`Core/Inc/debug_uart.h` 里新增了一个开关：

```c
#define DEBUG_RAW_UART   0   /* 0=日志走协议(正常)  1=直接打 ASCII(排障) */
```

**什么时候改成 1**：怀疑串口链路本身有问题、或者想确认"H723 到底活着没有"时。
改成 1 之后，**随便找个串口助手（115200）接上 USART1 就能看到完整的启动日志**，
连地瓜派都不用接。代价是协议流被文本冲乱，只能用来查问题。

## 四、联调步骤（严格按顺序，每步都有"期望"和"不对怎么查"）

### 第 0 步：只上电 H723，不放机上程序

> **不接任何东西的最快自检**：烧写后上电，等 4 秒，用手掰云台 ——
> 应该明显变"硬"（能感到电机在抗）。这是因为固件走完启动流程后
> 会给两个电机持续发速度指令（0 速也是指令，驱动器速度环会顶住）。
> 如果 4 秒后还是软的，说明没走到 RUNNING，按下面的步骤查。

```bash
# 在地瓜派上
python main.py ports                 # 找到串口设备名
python main.py ping --port /dev/ttyS1
```

**期望**：每 20ms 一帧遥测刷屏，最后打印"链路 OK"。

**不对怎么查**：

| 现象 | 原因 |
|---|---|
| 一个字节都没收到 | TX/RX 没交叉、没共地、H723 没上电 |
| 收到字节但 CRC 全错 | 波特率不一致（两边都改成 115200） |
| 收到遥测但 `state` 一直是 0 | H723 卡在 BMI088 初始化，看 TEXT 日志 |

### 第 1 步：看 H723 启动日志走到哪

`ping` 会把 H723 的 TEXT 原样打出来，按顺序应该是：

```
[H723] === YunTai Start ===
[H723] [BMI088] OK -> motor boot delay
[H723] [MOTOR] boot delay done
[H723] [MOTOR] enter closed loop
[H723] [MOTOR] set speed mode
[H723] [REF] pitch_motor(deg)=xx.xx      <-- 记下这个值
[H723] === STABILIZATION ACTIVE ===
```

**缺哪条就卡在哪一步**（沿用原来的排查习惯）。全程约 3.5s。

> `[REF] pitch_motor(deg)` 这个数很关键：如果它打印出来一直是 `0.00`，
> 说明**俯仰编码器反馈没收到**，此时俯仰会退化成"纯陀螺前馈"，
> 只能抵消转动、不能精确定位 —— 后面瞄准会差很多。
> 遇到这种情况先查 CAN2 接线和驱动器 ID。

### 第 2 步：确认俯仰位置环是活的

在上位机里跑：

```bash
python main.py run --no-laser --duration 20
```

看 H723 每 0.5s 的 `[DBG] P p=.. t=.. o=..`：

* `p`（编码器角）应随你**用手转动俯仰机构**而变化
* 你手转开之后，`t`（目标）不动，电机应该把 `p` 拉回 `t` 附近
  —— 这就是位置环在工作的表现

**如果 `p` 不变**：编码器没反馈 → 检查 CAN2。
**如果电机朝一个方向狂奔**：位置环方向反了，代码里有 400ms 的失控保护会
自动降级并报故障 `fault=0x02`。看到这个就说明**编码器符号与电机方向相反**，
需要把 `PITCH_KP` 暂时改成负数（或把 CAN2 的电机接线反一下）后再试。

### 第 3 步：确认偏航偏置真的被接受

```bash
python main.py run --no-laser --duration 20 --set control.kp=0.0
```

（`kp=0` 表示上位机不下发变化的偏置，云台就停在锁定的朝向上）

然后**用手把车体（云台底座）慢慢转一个小角度**：云台应该反向跟过来，
使平台朝向保持不变。这就是"稳"。

### 第 4 步：确认俯仰前馈方向

用手**快速前后倾**底盘：俯仰电机应该立刻反向跟动（能看到 `[DBG] o=` 明显变化）。
如果方向反了（越倾越跑），把 `yuntai_task.c` 里的
`PITCH_FF_SIGN` 从 `-1.0f` 改成 `+1.0f`。

同理偏航的 `YAW_FF_SIGN`：快速左右扭底盘，如果偏航顺着转的方向越跑越快，
就把它取反。

### 第 5 步：开激光，跑完整瞄准

```bash
python main.py run --duration 20 --budget 4
```

**期望**：
1. 地瓜派打印 `H723 ...` 的启动日志
2. 状态机 `BOOT_WAIT -> ACQUIRE -> LOCK`
3. 打印 `★ 锁定靶心：用时 x.xxs，误差 x.xx px`
4. H723 的 `[DBG]` 里俯仰指令 `o` 在零点附近小幅活动

**如果云台越修越偏、最后飞出去** → 上位机的 `sign_yaw/sign_pitch` 反了，
跑 `python tools/calib_boresight.py` 重标。

### 第 6 步：车体倾斜补偿（可选，默认关着）

`yuntai_task.c` 里 `PITCH_PLAT_COMP` 默认是 `0`。等前面都通了、要跑
"行驶中连续瞄准"时再打开，符号判法见代码里的注释。

### 第 7 步：跑完一圈后解绕

```bash
python main.py unwind --duration 10
```

**期望**：打印的相对偏航角从 -270°（跑一圈的量）慢慢回到 0，
最后出现 `[H723] [UNWIND] done -> reference re-locked`。

> 最后那句 "reference re-locked" 很关键，说明固件把**保持目标搬到了解绕后的
> 新姿态**。少了这一步，解绕一结束角度环就会把平台转回旧朝向，
> 线又被拧回去 —— 等于白解一场（这个逻辑在 `yuntai_task.c` 里有详细注释）。

| 参数 | 默认 | 什么时候动它 |
|---|---|---|
| `YAW_KP/KI/KD` | 200/30/10 | 偏航慢漂跟不回来 → 加大 KI；抖 → 减小 KP |

| `PITCH_TRAVEL_LIMIT_DEG` | 80 | 防撞机构/防扯线，一般不动 |
| `PITCH_RUNAWAY_DEG/MS` | 25°/400ms | 失控保护，一般不动 |
| `MOTOR_BOOT_DELAY_MS` | 2000 | **只有确认驱动器自检更快才能改小**，改错会"上电失去控制" |

## 五·补：云台上电后朝一个方向慢慢转 —— 陀螺零偏（已修复）

**现象**：上电后云台以很慢但恒定的速度朝一个固定方向转（比如顺时针）。

**根因**（不是机械问题，也不是 PID 问题）：

```
陀螺静止时读数不是精确的 0，而是一个固定小偏置 b（BMI088 典型 0.5~3°/s）
        ↓
Mahony 把陀螺积分成偏航角 -> 角度以恒定速率 b 漂走
        ↓
偏航 PID 看到"角度在漂"，就驱动电机去追
        ↓
结果：平台真的以 b 的速度匀速转 —— 看起来就是"慢慢朝一个方向转"
```

这也是文档 §2.6 里说的"偏航没有绝对基准"的同一个物理事实：
加速度计能修俯仰/横滚（有重力做基准），但**修不了偏航**（没有磁力计就没有方位基准）。

**修法**：把零偏标定塞进**本来就在等的那个 2 秒**（`MOTOR_BOOT_DELAY_MS`）里，
一分钱额外时间都不花，而且**完全保留"启动路径只允许纯延时"的铁律**：

```c
/* 无条件累加，不判断、不重来；时间到就用平均值 */
gyro_sum[i] += gyro[i];
gyro_n++;
...
bias[i] = clamp(gyro_sum[i] / gyro_n, ±0.10 rad/s);
```

⚠ 老代码的写法是"必须连续采够 N 个、且每个都在静止阈值内，否则清零重来"——
那样一旦传感器零偏本身就超过阈值就永远采不满，只能干等到超时，
更糟的是会卡住整个启动流程。**那个坑不能再踩。**

**现场规矩**：**上电后 2 秒内别碰云台**（这 2 秒在采零偏）。
启动日志里会打印标定结果：

```
[H723] [GYRO] bias(dps) x=.. y=.. z=..
```

正常应该在 ±1°/s 以内；明显偏大就重新上电再试一次。

> 为什么 `PITCH_KP` 要 100 而不是常见的个位数：
> 电机有静摩擦脱困转速（约 10rpm），换算到角度上是死区
> `死区 = 脱困转速 / KP`。KP=10 时死区 1.0°（1.1m 处 19mm，几乎顶满指标），
> KP=100 时死区 0.1°（1.1m 处 1.9mm）。200Hz 下这个增益相位裕度仍然很足。
